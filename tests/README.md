# Reproducing the evaluations

These are the two scenarios used while developing the skill:

| Scenario | Starting state | Behavior exercised |
| --- | --- | --- |
| `default` | One complete group, one partially complete group, two pending groups in total; existing untracked files | Skip completed tasks, fresh workers per pending group, preserve user work, review before checking tasks, leave changes uncommitted |
| `stacked-prs` | Two pending groups, a clean placeholder branch, and a local bare Git remote | One reviewed group per PR, correct dependency bases, committed completion markers, top branch checkout, resume without duplicates |

`fixtures/` contains the original starting artifacts; machine-specific requests
are regenerated by the setup command. `outputs/` contains the
implementations and unittest files produced by the original workers. `results/`
contains their historical run records and mock PR registry. Machine-specific
paths were replaced with `<evaluation>` and `<checkout>`; historical worker IDs
and commit hashes are evidence from those runs, not live resources in this repo.
The default run predates the stacked-mode addition; the stacked run includes it.

## Offline automated checks

From the repository root:

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

This reruns the 16 preserved implementation tests and exercises fixture setup,
the PR mock, branch relationships, and result verification using temporary local
repositories. It does not invoke an LLM or reproduce an agent's review judgment.

## Continuous integration

[Tests](../.github/workflows/tests.yml) runs the same offline command on GitHub
Actions for every push and pull request, and can also be dispatched manually.
The matrix covers Python 3.9 and 3.13 on Ubuntu 24.04. Python and Git are enough;
the suite needs no extra Python packages, OpenSpec installation, model credentials,
or access to a real PR service. Live agent evaluations and OpenSpec CLI validation
remain separate from this offline suite.

## Run with a real orchestrator

Choose a model supported by your agent host and prepare a new destination:

```sh
python3 tests/evaluate.py prepare default --directory /tmp/openspec-default-eval --model '<model>'
python3 tests/evaluate.py prepare stacked-prs --directory /tmp/openspec-stack-eval --model '<model>'
```

Each command creates a separate `repo/`, an `evaluation.json` manifest, and a
`REQUEST.txt` containing a complete prompt with paths for your checkout. The
destination must not already exist. The stacked scenario also creates a local
bare `remote.git` and an executable `mock-gh` that implements the small subset
of GitHub CLI commands used by the skill.

Start a fresh Codex or Claude Code conversation inside the generated `repo/`
and ask it to carry out `../REQUEST.txt`. Keep the evaluator scoped to that
directory. For the stacked scenario, all pushes go to its local `origin`, and
all PR operations must use its absolute `mock-gh` path. The mock does not
contact GitHub; its URLs use `example.invalid`.

After the agent finishes, verify the result:

```sh
python3 tests/evaluate.py verify /tmp/openspec-default-eval
python3 tests/evaluate.py verify /tmp/openspec-stack-eval
```

Verification runs the preserved behavior tests against the new implementation,
checks task completion and preserved files, validates the OpenSpec change, and
checks publication invariants where applicable. It requires the OpenSpec CLI.

For the stacked scenario, verify once, ask the same orchestrator to resume the
completed request, and verify again. The first verification saves a fingerprint
of branches, commits, PR IDs, and tasks; later verifications reject duplicates
or mutations to a completed run. Use a new destination for another evaluation.

Inspect the orchestrator's run record as well: confirm distinct worker IDs per
group, the requested model parameter, review before acceptance/publication, and
no extra workers on resume. Git state alone cannot prove those behaviors or the
effective model. The historical native runtime did not expose effective-model
metadata, and the mock has no remote CI or human review.

Repair rounds, publication-failure recovery, restacking after repairs, and a
Claude-hosted run were not exercised in the original evaluations. The included
results do not claim coverage for them.
